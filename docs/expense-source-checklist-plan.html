Feature plan · August 2026

Monthly expense source checklist

Give each monthly budget a lightweight review list for statements and accounts, so reconciliation is visible and can be checked off without coupling it to individual purchases.

Feature decisionUI mocksImplementationTesting

1. Feature decision

Use reusable, user-owned expense-review sources with separate completion state for each monthly budget. A source is a statement or account to review, not the existing Purchase.source field.

Recommended experience: place “Expense review” in a narrow companion rail to the right of the monthly budget’s main content. Keep it sticky while the main column scrolls, and stack it below the main content when the viewport cannot support two readable columns.

Locked behavior

  • The reusable source list starts empty; examples below are illustrative only.
  • Completion is always manual and applies only to the displayed month.
  • New months begin unchecked. Archived sources leave active checklists but retain history and can be restored.
  • No purchase counts, totals, name matching, or automatic completion are involved.

3. Implementation plan

Step 1 · Persistence

Independent checklist models

Add ExpenseSource and ExpenseSourceCheck. Enforce per-user names and one completion row per monthly budget/source pair. Register both in admin and add factories.

Step 2 · Monthly context

Read active sources and state

Build checklist items from active user-owned sources and any completion rows for the displayed month. Do not write database rows during a page GET.

Step 3 · HTMX endpoints

Toggle and manage inline

Add authenticated, user-scoped endpoints for monthly toggles and a modal that creates, renames, archives, and restores reusable sources.

Step 4 · Templates and CSS

Integrate the companion rail

Wrap the monthly page in a main/aside grid, widen only this page’s content container, and keep the checklist rail sticky on desktop. Collapse to one column below the desktop breakpoint while preserving native controls, focus states, and touch targets.

4. Testing and acceptance

  • Model uniqueness, monthly independence, checked timestamps, and archive history.
  • Empty and populated monthly-page states plus progress counts.
  • Cross-user protection on every management and toggle operation.
  • Proof that matching Purchase.source text has no checklist effect.
  • HTMX partial updates, ordinary POST redirects, mobile layout, and keyboard interaction.
